- **2026-08-21 — the check that makes description compression safe: a dropped-word report.** Compressing a description silently changes what auto-fires, and the verbatim-survival check used for moved text does not apply. Instead diff the *word sets*: `set(old_words) - set(new_words)`, minus stopwords, printed per skill. Across 62 rewrites it surfaced four genuine trigger losses that were then restored ("will this change break another routine", "is anyone working on X", "write loops not prompts", and the bot library names discord.py / hikari / slack_bolt / python-telegram-bot). Everything else it flagged was punctuation noise or deliberate. Pair it with per-file assertions — body byte-identical, every other frontmatter key round-trips, new frontmatter parses under a strict YAML parser with the description equal to the intended string — and emit the value as a **double-quoted** YAML scalar, since compressed prose reliably contains a colon-space that breaks an unquoted one.

- **2026-08-21 — the safe mechanism for bulk prose surgery: anchor-pair slicing with a conservation assertion.** Address each passage by a (start_anchor, end_anchor) pair and let the script cut between them, so the text is MOVED rather than retyped. Validate every anchor before writing anything and abort on a missing, ambiguous (count != 1), or overlapping span; then assert `removed_chars - pointer_chars == original_len - new_len`, and assert each moved chunk appears verbatim in its destination. That trio makes silent loss impossible, and the abort-first pass means a bad anchor costs a re-run rather than a mangled file. Follow it with a presence check on the load-bearing imperatives by name (17 of 17 here) — conservation proves nothing was *lost*, only the named check proves nothing important was *relocated out of reach*.

- **2026-08-21 — capping chat length: the correct model is REPEATED capping, and the naive one inverts the answer.** A model that caps once and lets the remainder run as a single fresh chat says later caps are better (cap-40 saves 19%, cap-100 saves 10%, cap-20 only 13%) — because it charges the 100k floor only once. Model it as *repeated* chunks with a per-restart re-orientation penalty and the answer flips: over today's 64 sessions / 1,737 real calls, with a 4-6 call penalty per restart, capping at **15-30 calls (~120-200k) is the flat optimum at 34-39% cheaper than uncapped**; cap-60 saves 23%, cap-80 only 17%. So the existing "archive by ~100-120k" line in `~/.claude/CLAUDE.md` is **well calibrated and should not be moved later** — the intuition that frequent restarts are expensive is wrong at this scale, because context growth outruns the floor. Below ~15 calls the floor does start to dominate. The counterfactual is written into `context-tripwire.py`'s docstring so the next session that wants to "relax the nag" has to re-run the model first.
