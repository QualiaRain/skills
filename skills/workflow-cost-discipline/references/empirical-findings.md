# workflow-cost-discipline — Empirical findings (the receipts)

The measured token-accounting behind the routing/cost guidance in [`../SKILL.md`](../SKILL.md). **Read this before any new cost probe, or when you need to justify a routing or cost number.** To re-measure, follow the cheap measurement recipe below (the original `cost-routing-diagnostic` script was never saved as a reusable workflow). The actionable one-line takeaways are already summarized inline in SKILL.md (Haiku ~3.4× Sonnet's context; ~99% of an agent's cost is context; same-model cache shares only past the concurrency wave; `+Nk` counts output only) — this file is the detailed evidence + methodology.

- **Cheap measurement recipe (how these numbers were gotten — use it before any new cost probe).** Read per-agent cost from the **subagent transcripts**, never from in-script `budget.spent()` (proven unreliable): after a run, the Workflow result gives a transcript dir → glob `agent-*.jsonl`, grep `model` / `cache_creation_input_tokens` / `cache_read_input_tokens` / `output_tokens`; `journal.jsonl` lists agents in start order. Keep probe agents **trivial** (one-line plain-text prompt, no schema) and use the **smallest N that answers the question** (2–3 settle most; ~20 mapped the ~15 concurrency cap). Cache tests: **sequential** (`await` each) tests reuse of a *committed* cache; **`parallel()`** tests cold-concurrent; use a **fresh prompt each run** so you don't read a prior run's warm cache. To inspect *what's* in context, have an agent self-audit (quote a tool schema, name its biggest block) — but cross-check against the token count, since agents under-report their own bulk.
- **2026-05-30, minimal 3-agent run (Haiku + Sonnet + Opus); numbers from the subagent transcripts.** Routing confirmed: 3/3 ran on their assigned model (`claude-haiku-4-5`, `claude-sonnet-4-6`, `claude-opus-4-8`), all correct. **Output was negligible** - 109 / 122 / 225 tokens - while **input/context dominated**: cache-creation 77,674 / 20,325 / 31,678 tokens (system prompt + CLAUDE.md + tool schemas each agent loads). ~99% of an agent's cost is the context it carries, not what it writes. **Lesson: agent COUNT x per-agent context size is the dominant cost driver; model choice mostly sets the *price* of those tokens. Minimize fan-out; do in plain script code anything that doesn't need an agent; even a minimal workflow has a tens-of-thousands-of-tokens-per-agent floor.**
- **`budget.spent()` / `+Nk` budgets count OUTPUT tokens only** - and real output was ~0.3% of *this run's token volume* (a low-output mechanical probe: ~225 out/agent, no extended thinking). **So `+Nk` barely constrains cost *on low-output mechanical fan-outs* — their input-dominated spend can sail past the cap.** It is **not** weak in general: thinking is output-billed and the budget pool is shared across the main loop and all workflows, so on extended-thinking / xhigh / ultracode runs `+Nk` becomes a genuinely *binding* ceiling. Control mechanical-fan-out spend through agent count + per-agent context size + model price; use `+Nk` as the hard throw-stop, tightest on output/thinking-heavy work.
- **In-script `budget.spent()` deltas are NOT reliable for per-agent attribution (methodological finding; corrects an earlier wrong call).** The diagnostic reported Haiku at 13,806 "output tokens" from `budget.spent()` deltas - but the transcript shows Haiku made one clean `StructuredOutput` call and emitted **109** (Sonnet 122, Opus 225). The budget-delta figure was off by ~100x for the first agent. `budget.spent()` is documented as a *shared pool across the main loop and all workflows*, not a per-agent output meter - which likely explains leakage onto the first/background agent - but it did not cleanly reconcile with `/usage`, so treat the exact mechanism as undetermined. **Haiku did NOT thrash; the earlier "Haiku ballooned its output" claim is retracted.** Lesson: measure per-agent cost from the subagent transcript usage blocks (`cache_creation` / `cache_read` / `output_tokens`), never from in-script `budget.spent()` deltas while the main loop is active.
- **2026-05-30 v2 (controlled re-run: Sonnet then Haiku, order reversed).** Per-agent context is **model-driven, not position-driven**: Sonnet 20,030 (now 1st) vs 20,325 (v1, 2nd); Haiku 67,387 (now 2nd) vs 77,674 (v1, 1st) - each model carries the same context regardless of order. The earlier budget-delta inflation tracked **concurrent main-loop output**, not the agent: v1's first agent showed 13,806 (a long launch message + heavy Opus thinking ran alongside it), v2's first agent showed 112 (short message). Definitively confirms Haiku never misbehaved.
- **Counterintuitive cost finding: Haiku is NOT automatically cheaper for small agents.** Haiku loads ~3.4x more context per agent than Sonnet (~67-78k vs ~20k) for identical work - real context, not tokenizer noise (3.4x far exceeds any tokenizer gap). **Cause pinned 2026-05-30: Haiku eager-loads every connected MCP tool's *full* schema while Sonnet/Opus defer them to names — so this penalty is conditional on MCP servers being connected; disconnect them and Haiku ≈ Sonnet (~18k). See the MCP/tool-loading finding below.** By rough public price ratios (Sonnet input ~3-4x Haiku), Sonnet's 20k is roughly on par with Haiku's ~67k in actual cost, so at small sizes Haiku's price advantage is **largely canceled** by its context overhead - the two are comparable and Sonnet brings more capability for about the same money. **Lesson: don't reflexively route small/numerous agents to Haiku for "cheapness" - the saving is mostly illusory at small sizes. Sonnet is usually the better default; reserve Haiku for genuinely high-volume mechanical work that amortizes its larger fixed context. Measure, don't assume.**
- **2026-05-30, same-model cache-sharing test (resolves Open Q#1; numbers from subagent transcripts).** Two 3×Haiku runs, byte-identical trivial prompt, no schema. **Sequential** (await each before the next): #1 cache_creation **75,127** / read 0; #2 & #3 cache_creation **0** / read **75,127** each — a 100% prefix hit, zero re-creation. **Parallel** (3 fired concurrently via `parallel()`, with a *different* fresh prompt so Run-1's warm cache couldn't confound): all 3 cache_creation **64,839** / read **0** — every agent re-created the full prefix, none shared. **Verdict: same-model agents share a prompt cache only across a *committed* entry. A staggered/later agent reads the whole prefix at read price (~0.1×); a simultaneously-started wave shares nothing — no entry is committed when the others start, so all miss.** Cost (write 1.25× / read 0.1× base input): a cache-warm same-model agent's context ≈ 8% of a cold one; the parallel trio paid the full 3× (zero benefit). **Fan-out model (concurrency cap ~16):** the first ~16 same-model agents start cold and each pay full context; only the tail (N>cap) reads cheap. So fan-outs **≤ ~16 same-model agents get NO cache benefit** (agent-count × per-agent-context holds in full); **>> 16** amortize (≈16 full + the rest at ~0.1× → roughly 4× cheaper at N=100, approaching ~12.5× at the limit). The N>cap tail-amortization is now **directly confirmed** (2026-05-30 follow-up, 20×Haiku via `parallel()`): the run split **15 create / 5 read** — the 5 readers were *exactly* the last 5 agents started, each reading the full 64,839 prefix at 0.1×; the cold-concurrent first wave measured **≈15** here (≈ the 16 cap). Cost: ~23% under all-cold at N=20, widening with N (≈4.6× cheaper at N=100, →~12.5× at the limit). (Per-agent Haiku context was ~64.8k with computer-use *absent* vs **75,127** with it present — the ~10k difference is computer-use's ~26 MCP tool schemas, since Haiku eager-loads every connected MCP tool's full schema; see the MCP/tool-loading finding below.)
- **Same-model grouping optimization (consequence of the above):** grouping agents by model captures cache savings **only where a warm prefix is reused** — the part of a same-model group *beyond* the first concurrency wave, or a later same-model phase reusing an earlier phase's still-warm prefix (~5-min TTL). A single same-model wave ≤ cap saves nothing on cache. So: don't promise cache savings for small same-model fan-outs; for large ones expect roughly *first-wave-full + tail-at-0.1×*, **not** the naive "one writes, all the rest read."
- **2026-05-31, `pipeline()` cross-stage cache reuse (extends the cache-sharing findings).** 2-stage same-model `pipeline([1,2], stageA, stageB)`, *different* prompt per stage: stageA (cold concurrent) created the full **75,205** prefix each; stageB read **70,453 (94%) at 0.1×**, creating only its 4,751-tok suffix — so it's the shared **prefix** (system+tools+CLAUDE.md) that caches, not the whole prompt. **`pipeline()` vs `parallel()` doesn't itself change amortization — temporal *staging* + *same model* does.** A barrier-separated `parallel` stage gets the identical cache benefit; `pipeline` just delivers it with no barrier stall (strictly ≥ `parallel`: same cache, better wall-clock). **Cost model: a same-model M-stage pipeline ≈ one cold first-wave + everything else (later stages + the >cap tail) at ~0.1×, NOT N×M×base.**
- **Per-agent context = a ~18k base + (Haiku only) the full schema of every connected MCP tool. RESOLVED 2026-05-30 by direct agent introspection — supersedes two earlier mis-calls on this.** Default-agent context measured **Haiku 65,044 vs Sonnet 17,687** (identical setup). The gap is *not* intrinsic model bloat or a bigger system prompt — it's **tool-loading policy**: shown an MCP tool, **Haiku quoted its full `notion-fetch` schema** (and named its biggest block "~80 tool definitions, ~90% of context"); **Sonnet saw only the bare name** ("true for all deferred tools"; its biggest block was CLAUDE.md). So **Haiku eager-loads the whole toolbox (~70 MCP schemas ≈ ~47k); Sonnet/Opus defer MCP tools to names** (the ToolSearch mechanism). Strip MCP and both models sit at ~18k base (core tool schemas + CLAUDE.md + skills list). **Correction:** the original *"connected MCP servers tax every subagent"* finding was RIGHT **for Haiku** and shouldn't have been retracted — the computer-use 75,127→~65k drop was real (~26 schemas ≈ +10k); the reconnect test that prompted the retraction was flawed (the app-level reconnect never re-propagated computer-use into the subagent toolset). **Safe levers, no calibration loss: (1) before a Haiku fan-out, disconnect MCP servers you don't need that run → each Haiku agent ~65k → ~18k; (2) or use Sonnet, which defers MCP automatically (~18k regardless). With unneeded MCP disconnected, Haiku at ~18k *and* lower per-token price is genuinely the cheapest option for mechanical fan-outs.** Lean *custom* agents stay off the table (the owner: calibration risk) and are now unnecessary — MCP-disconnect + model choice get the win safely. (Measured Haiku agentType spread: general-purpose 65k · claude-code-guide 42k · statusline-setup 7k — a restricted-tool agentType also dodges the MCP eager-load.) **Status — undocumented & likely transient:** Anthropic's documented direction is the *opposite* (defer all tools to save context — built-in deferral shipped v2.1.69; API `defer_loading`). Subagents not deferring MCP is filed as a **bug** ([claude-code#37793](https://github.com/anthropics/claude-code/issues/37793): subagents inherit full MCP JSON schemas and overflow Sonnet's 200k), and the fix is rolling out unevenly across models (Sonnet subagents already defer; Haiku ones don't *yet*). Treat the Haiku eager-load as **current behavior, not a contract** — re-measure as Claude Code updates; the gap may close.

- **2026-05-31, reading `/usage` for a workflow run (so a big number doesn't trigger a false alarm).** Raw `/usage` token deltas **overstate real cost** when cache-read-dominated: a 4-Sonnet web-research run showed **+2.6M total but ~96% was 0.1× cache-read** (the finders' multi-turn re-reads across 77 fetch turns + a little main-loop) → effective cost ≈ **0.4M input-equiv, ~6× under the headline**. **Weight any delta by 1.25× (cache-write) / 0.1× (cache-read) / output before judging a run.** Two introspection methods: per-agent truth from the subagent transcripts (recipe above); and **main-loop + exact per-tool MCP composition from `/context` on a *forked* chat** — free, it itemizes every MCP tool's schema size and splits active vs deferred (this is how the exact per-connector table in memory was built — no toggle dance needed). Caveat: the `/usage` *summary* surfaced agent cache-reads but not agent cache-writes, so treat it as main-session-centric and use transcripts for per-agent cost.

- **2026-06-04, Workflow `args` → `TypeError: args.map is not a function` — root cause was a caller-side stringify, NOT `args` "arriving unparsed."** The official contract (live tool spec + workflows doc): pass `args` as an **actual JSON array value** in the tool call and the script can call `args.map`/`args.filter`/`args.flatMap` on it directly, no parse. That `TypeError` is the textbook symptom of passing `args` as a **JSON-encoded string** — a stringified list reaches the script as one string, so array methods throw. **Correct pattern: pass a real JSON array** (`args: ["a","b"]`, *not* `args: "[\"a\",\"b\"]"`); then `args.map` just works. If you want a defensive guard, **fail loudly** on a non-array — `if (!Array.isArray(args)) throw new Error('args must be a JSON array, not a string')` — and **never** silently substitute a hardcoded `DEFAULT_NAMES` list: that defeats `args`' whole purpose (parameterizing a reusable/saved workflow) by making it process **stale baked-in data** whenever `args` is unexpected, while masking the calling error; and a `JSON.parse(args)` branch re-introduces the exact stringify path the spec says to avoid.
